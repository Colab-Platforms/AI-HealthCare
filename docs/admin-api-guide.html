1. How the approval flow works (the core idea)

An Admin or Take Admin never changes sensitive data directly. They send a request. Only the Super Admin can approve it. The real record changes only after approval.
1
Admin / Take AdminSends POST /requests with module, record id, new value and a reason.Server saves the old value and sets status pending_approval. The real data is unchanged.
2
Super AdminOpens GET /requests?status=pending_approval then GET /requests/:id.Sees old value and new value side by side, who asked, and why.
3
Super AdminChooses one: Approve, Reject (reason required) or Request changes.
4
Server checksApprover is not the requester. Record has not changed since the request. High-risk actions need a second, different Super Admin.
5
Server executesUpdates the real record and sets status executed. If the update fails the status is execution_failed, never "done".
6
EveryoneEvery step is saved in the audit log (GET /audit-logs). The requester sees the final status in "My Requests".

Statuses: pending_approval, under_review, changes_requested, approved, rejected, executed, execution_failed, cancelled.

Example: a user's height is saved as 15 cm. Admin A requests 150 cm with the reason "user confirmed, ticket #1042". Super Admin approves. The profile now shows 150 cm and the audit log has the whole history.

2. Admin panel (/admin, role admin)

Daily work: users, support, report status. Can view what the job needs, and send requests for sensitive changes.

GET/me/permissionsBUILTWhat this role is allowed to do. Used to build the left menu.

Response

{
  "role": "admin",
  "permissions": {
    "users": ["VIEW", "REQUEST"],
    "health_profiles": ["VIEW", "REQUEST"],
    "food_database": ["VIEW", "REQUEST"],
    "support_tickets": ["VIEW", "EDIT"],
    "approvals": ["CREATE", "VIEW"],
    "audit_logs": ["VIEW"]
  }
}
POST/requestsBUILTCreate a change request: fix a health profile, block a user, add/fix/remove a food item.

Request body

{
  "module": "health_profiles",
  "recordId": "665f1c2e9b1d4a0012ab34cd",
  "action": "edit",
  "newValue": { "height": 150 },
  "reason": "User confirmed by chat, ticket #1042",
  "priority": "normal"
}

Response

{
  "_id": "6660aa11bb22cc33dd44ee55",
  "requesterRole": "admin",
  "module": "health_profiles",
  "action": "edit",
  "oldValue": { "height": 15, "weight": 72 },
  "newValue": { "height": 150 },
  "reason": "User confirmed by chat, ticket #1042",
  "priority": "normal",
  "highRisk": false,
  "status": "pending_approval",
  "executionStatus": "not_run",
  "submittedAt": "2026-11-23T10:30:00.000Z"
}

Possible errors

400 Reason must be at least 10 characters
400 Module not approvable: <module>
403 Role cannot raise requests for <module>
404 Record not found

3. Take Admin panel (/take-admin, role takeadmin)

Business growth: analytics, campaigns and food drafts. Sees group totals only, never one patient's clinical data. Groups smaller than 10 users are hidden.

Take Admin uses the same request APIs as Admin: POST /requests, GET /requests, GET /requests/:id, POST /requests/:id/cancel, GET /audit-logs and GET /me/permissions. See section 2 for request and response. The difference is what they send:
POST/requests (food draft)BUILTAdd, fix or delete a food item. Super Admin approves before it is published.

Request body: add a food

{
  "module": "food_database",
  "action": "create",
  "newValue": { "name": "Bajra Rotla", "state": "Gujarat", "calories": 120 },
  "reason": "Missing Gujarati food, source: IFCT 2017"
}

Response

{ "module": "food_database", "action": "create", "status": "pending_approval", "highRisk": false }

Delete a food

{ "module": "food_database", "action": "delete", "recordId": "<food id>", "reason": "Duplicate item" }
-> response has "highRisk": true, "priority": "high" (needs two Super Admins)

4. Super Admin panel (/super-admin, role superadmin)

Controls everything: approves or rejects requests, manages admins, sees all audit logs.

GET/requests?status=pending_approvalBUILTApproval Center list: every request from every admin (oldest first by your sort).

Response

{
  "items": [
    { "_id": "6660aa11...", "requesterId": { "name": "Admin A", "role": "admin" },
      "module": "health_profiles", "action": "edit", "priority": "normal",
      "status": "pending_approval", "submittedAt": "2026-11-23T10:30:00.000Z" },
    { "_id": "6660bb22...", "requesterId": { "name": "Take Admin B", "role": "takeadmin" },
      "module": "food_database", "action": "delete", "priority": "high",
      "highRisk": true, "status": "pending_approval" }
  ],
  "total": 2, "page": 1, "limit": 20
}
POST/requests/:id/approveBUILTApprove and run the change.

Request body

{ "comment": "Verified with user" }

Response (normal request)

{
  "status": "executed",
  "decision": "approved",
  "decidedAt": "2026-11-23T11:15:00.000Z",
  "executionStatus": "success",
  "executedAt": "2026-11-23T11:15:01.000Z"
}

Response (high-risk, first approval)

{ "status": "under_review", "highRisk": true }
A different Super Admin must call approve again to confirm.

Errors

403 Cannot approve your own request
403 A different Super Admin must confirm high-risk actions
409 Request is not awaiting a decision
409 Record changed since the request was made; sent back for fresh review
500 Approved but execution failed: <reason>   (status = execution_failed)
POST/requests/:id/rejectBUILTReject. A reason is required. Data stays unchanged.

Request body

{ "comment": "No document supports this height" }

Response

{ "status": "rejected", "decision": "rejected", "decisionReason": "No document supports this height" }

Errors

400 Rejection requires a reason
403 Cannot decide your own request
POST/requests/:id/request-changesBUILTAsk the requester for more information.

Request body

{ "comment": "Attach the ticket screenshot" }

Response

{ "status": "changes_requested", "decisionReason": "Attach the ticket screenshot" }

5. Common errors (all APIs)

CodeMeaning
401Not logged in, or the token is invalid or expired
403Your role is not allowed to do this (also saved in the audit log as blocked)
400Missing or invalid input
404Record or request not found
409Wrong state, for example approving a request that was already decided
500Server error, or approved but the update failed

Example responses are written from the code, not from live calls, so real IDs and timestamps will differ.
